# 大模型 Badcase 解决实践指南

> 业务场景下常见问题的诊断思路与解决策略优先级

---

## 问题诊断与解决策略

### 1. 复读机、基础逻辑缺陷

#### 问题表现
- 模型重复输出相同内容
- 基础逻辑错误（如"9.11 > 9.8"判断错误）

#### 根因分析
**基座能力不足**
- 预训练数据质量问题
- 模型规模/参数量不足
- 训练目标设计缺陷

#### 解决方案
| 方案 | 可行性 | 成本 | 效果 |
|-----|-------|------|------|
| **Prompt 优化** | ❌ 无效 | 低 | 无法解决 |
| **SFT/RL 微调** | ❌ 无效 | 中 | 无法解决 |
| **预训练优化** | ✅ 有效 | **极高** | **根本解决** |

**结论**：
- 单靠提示词、微调**无法解决**
- 需通过提升预训练数据质量与规模，或优化训练目标
- **成本高、难度大**，需要基座团队支持

---

### 2. 安全/客服领域的拒绝回答话术判断不佳

#### 问题表现
- 该拒绝时不拒绝（安全风险）
- 不该拒绝时过度拒绝（体验差）

#### 解决方案

**Step 1: Prompt 调优**
- 尝试用 system prompt 控制
- 如果**不能很好控制**，进入下一步

**Step 2: 构造微调数据集**
- **Badcase 作为负样本**（错误输出）
- **正确输出作为正样本**
- 可使用**数据蒸馏**构造更多训练样本

**Step 3: 模型微调**
- **SFT**：让模型记住正确回答模式
- **RL/DPO**：强化正确行为，抑制错误行为

---

### 3. 生成话术单一

#### 问题表现
- 回答模板化、缺乏变化
- 用户体验单调

#### 解决方案

**方案 1: 采样参数调整（优先尝试）**
| 参数 | 作用 | 建议值 |
|-----|------|-------|
| **Temperature** | 控制随机性 | 提高（如 0.7→0.9）|
| **Top K** | 限制候选词数量 | 增大（如 20→50）|
| **Top P** | 核采样阈值 | 提高（如 0.9→0.95）|

**方案 2: Prompt 工程**
- 要求模型"用不同方式回答"
- 提供多样化示例（Few-shot）

---

## 前置处理与后置处理

当 Prompt 调优无法解决问题时，考虑在模型**外部**构建处理流程：

### 前置处理（输入侧）

```
用户输入
    ↓
┌─────────────────────────────────────┐
│ 1. 关键词过滤（规则匹配）              │
│    - 敏感词拦截                       │
│    - 问题类型识别                     │
├─────────────────────────────────────┤
│ 2. 分类模型                           │
│    - 问题意图识别                     │
│    - 路由到不同处理流程               │
├─────────────────────────────────────┤
│ 3. 大模型改写（Query改写）            │
│    - 问题规范化                       │
│    - 意图澄清                         │
└─────────────────────────────────────┘
    ↓
大模型生成
```

**典型应用**：
- **安全过滤**：拦截敏感提问
- **意图识别**：区分闲聊/业务问题
- **Query改写**：把口语化问题改写成标准查询

### 后置处理（输出侧）

```
大模型输出
    ↓
┌─────────────────────────────────────┐
│ 1. 内容过滤（规则/模型）              │
│    - 敏感内容检测                     │
│    - 格式合规检查                     │
├─────────────────────────────────────┤
│ 2. 检索规则匹配                       │
│    - 检索标准答案库                   │
│    - 替换模型生成内容                 │
├─────────────────────────────────────┤
│ 3. 大模型二次判断                     │
│    - 自检：回答是否合理？             │
│    - 质检：是否符合规范？             │
└─────────────────────────────────────┘
    ↓
用户看到的结果
```

**典型应用**：
- **安全拦截**：检测生成内容是否合规
- **事实核查**：对比知识库，过滤幻觉
- **格式规范**：统一输出格式

## 业务场景解决策略优先级

> **由浅入深，成本由低到高**

```
┌─────────────────────────────────────────────────────────────┐
│  Level 1: Prompt 工程（零成本）                               │
│  • In-context Learning（Few-shot）                          │
│  • Chain-of-Thought（思维链）                                 │
│  • System Prompt 调优                                         │
└─────────────────────────────────────────────────────────────┘
                           ↓ 效果不佳
┌─────────────────────────────────────────────────────────────┐
│  Level 2: 前后置处理模块（低开发成本）                         │
│  • 前置：关键词过滤、分类模型、Query改写                       │
│  • 后置：内容过滤、检索规则、二次判断                          │
└─────────────────────────────────────────────────────────────┘
                           ↓ 仍不满足
┌─────────────────────────────────────────────────────────────┐
│  Level 3: Agent / 工具增强（中等成本）                         │
│  • Function Call / Tool Use                                  │
│  • MCP（Model Context Protocol）                             │
│  • RAG（检索增强生成）                                        │
└─────────────────────────────────────────────────────────────┘
                           ↓ 需要改变模型行为
┌─────────────────────────────────────────────────────────────┐
│  Level 4: 数据蒸馏 + SFT（高数据成本）                         │
│  • 收集 Badcase 构造数据集                                    │
│  • 数据蒸馏扩充样本                                          │
│  • 全参数微调（优先于 LoRA）                                  │
└─────────────────────────────────────────────────────────────┘
                           ↓ 需要强化特定偏好
┌─────────────────────────────────────────────────────────────┐
│  Level 5: RL / DPO（高训练成本）                              │
│  • DPO：偏好数据直接优化                                      │
│  • RLHF/GRPO：强化学习微调                                    │
└─────────────────────────────────────────────────────────────┘
                           ↓ 基座能力不足
┌─────────────────────────────────────────────────────────────┐
│  Level 6: 预训练优化（极高成本，小公司不考虑）                  │
│  • 数据质量提升                                              │
│  • 训练目标优化                                              │
│  • 模型规模扩展                                              │
└─────────────────────────────────────────────────────────────┘
```

### 核心原则

| 原则 | 说明 |
|-----|------|
| **1. Prompt 优先** | 能不调优就不调优，成本最低 |
| **2. 外部模块优先** | 用规则/分类模型/检索解决，不改模型 |
| **3. Agent 增强** | Function Call / MCP 扩展能力边界 |
| **4. 谨慎微调** | 能不微调就不微调，避免灾难性遗忘 |
| **5. 全参优于 LoRA** | SFT 能全参就不要用 LoRA/QLoRA |
| **6. RL 作为最后手段** | DPO/RL 成本高，用于强化偏好 |
| **7. 小公司不做预训练** | 成本极高，用开源基座即可 |

## 不同问题的推荐策略

| 问题类型 | 推荐策略 | 不推荐 |
|---------|---------|--------|
| **复读机** | 调整采样参数 → 数据蒸馏 + SFT | Prompt（无效） |
| **逻辑错误（9.11>9.8）** | 换基座模型 | 微调（治标不治本） |
| **安全判断不准** | Prompt → 前置过滤 → SFT/RL | — |
| **话术单一** | 调整 Temperature/TopK | 微调（过度） |
| **幻觉严重** | RAG → 后置事实核查 | SFT（可能加剧） |
| **特定格式不对** | Few-shot Prompt → SFT | 预训练 |

## 面试要点

### 常见问题

**Q1: 模型出现"9.11 > 9.8"这类基础逻辑错误怎么办？**
- A: 这是**基座能力缺陷**，Prompt 和微调无法解决。需要：
  1. 换更强的基座模型
  2. 或让基座团队优化预训练

**Q2: 为什么建议"能不微调就不微调"？**
- A:
  1. **成本高**：数据收集、训练资源
  2. **风险大**：灾难性遗忘、泛化能力下降
  3. **迭代慢**：每次改数据都要重新训练
  4. **Prompt 和外部模块**通常能以更低成本达到类似效果

**Q3: 为什么 SFT 建议全参数而非 LoRA？**
- A:
  1. **效果上限更高**：全参能改变模型内部表示
  2. **LoRA 容量有限**：复杂任务可能欠拟合
  3. **除非显存限制**，否则优先全参

**Q4: 前置处理和后置处理各适合什么场景？**
- A:
  - **前置**：输入安全过滤、意图识别、Query改写
  - **后置**：输出生成质量检查、事实核查、格式规范

**Q5: 小公司解决 Badcase 的最佳实践？**
- A:
  1. Prompt 工程
  2. 前后置规则/模型
  3. RAG / Agent
  4. 数据蒸馏 + SFT
  5. **不要做预训练**

---

## 总结

```
Badcase 解决路径：
    Prompt 调优
         ↓（无效）
    前置/后置处理模块
         ↓（能力不足）
    Agent / RAG 增强
         ↓（需改变行为）
    数据蒸馏 + SFT（全参）
         ↓（需强化偏好）
    RL / DPO
         ↓（基座缺陷）
    换基座 / 预训练优化
```

**一句话原则**：**由浅入深，能不碰模型就不碰模型，能用规则就不用学习。**
